## Security notes (audited 2026-10-08 — accepted trade-offs, no action needed unless you disagree)
- **Stock counts are public by design.** Product pages show real stock honestly, so the database lets anyone read units on hand per hub (anyone with the public Supabase key can list them). If you don't want competitors to scrape exact stock, replace the public read of `inventory` with a function that returns "in stock / low / out" only.
- **Order tracking** is only reachable through the website's rate-limited form: the hardening migration (item 0) revokes direct calls to `track_order`, which needs the order number *and* the phone on the order and returns only status, city and items — never the address or phone. Until that migration is applied the function can still be called directly on the Supabase API without the per-IP limit.
- **Sessions last 30 days, but signing out (or an admin deactivating/resetting an account) revokes every earlier session server-side** (`profiles.sessions_revoked_at`, hardening migration — item 0), so a copied cookie stops working. Until that migration is applied a stolen cookie cannot be recalled; deactivate the account instead.
- **Content-Security-Policy allows inline scripts** because Next.js needs them for page hydration without per-request nonces (which would make every page uncacheable and slower). There is no raw-HTML rendering anywhere in the app (headline markup renders as escaped text), so the practical XSS surface is minimal.
- **Supabase advisor warnings (harmless):** five pure helper functions (`lagos_now`, `touch_updated_at`, …) have no fixed `search_path`; and the "security definer function executable" notices are the intended role-checked functions (verified with real data — see PROGRESS).
- **Retired role label.** `supplier` still exists in the database's list of role names (Postgres can't remove a single value without rewriting every access rule that uses roles). Nothing can use it: a database constraint (`profiles_no_supplier_role`) rejects any account with that role.
